# 인물 연결과 검토 — 2026-10-28

인물 후보가 여러 명일 때 첫 번째 후보를 고르던 처리를 제거했다. 탐지된 값의 치환은 계속 실행하며, 소유자를 확정할 수 없는 항목은 검토 목록에 남긴다. 이 단계의 목표는 잘못된 확정을 줄이고 검토량을 측정하는 것이다. 실제 고객 데이터에서의 우위나 재식별 방지를 입증한 단계는 아니다.

## 결정 규칙

- 명시적인 `subjects` 키는 표의 행 소유자를 정한다. 다른 scope의 같은 키 값은 외래키 소유자를 임의로 선택하는 근거로 쓰지 않는다.
- 알려진 값의 후보가 하나이거나, 행·참조 인물·유일한 강한 일치값의 문맥이 후보를 하나로 좁히면 연결한다. 행 소유자와 상담사 등 복수 후보가 경쟁하면 행을 무조건 우선하지 않는다.
- 여러 사람이 공유하는 이메일·전화·이름은 그 자체로 문서의 인물 근거를 만들지 않는다. 별도의 문맥으로 후보가 하나로 좁혀질 때만 연결한다. 유일한 후보도 완전한 현실 세계의 식별 증거는 아니다.
- subject 키가 없는 표에서는 알려진 이름·이메일·전화 후보의 교집합을 사용한다. 이름은 A, 이메일은 B인 행은 보류한다. 추론한 행의 값을 다른 행의 연결 근거로 재등록하지 않는다.
- 알려진 인물이 없는 이름은 **문서 내 임시 군집**만 만든다. 짧은 이름은 그 문서의 유일한 전체 이름에만 붙이며, 후보가 여러 명이면 보류한다. 표의 미확인 인물도 행별 임시 페르소나를 쓴다.
- 여러 인물이 문맥에 있는 일반 날짜·인구통계 값은 단일 소유자를 임의 지정하지 않는다. 명확한 생년월일 일치는 구분하지만, 공동 사건을 따로 모델링하는 기능은 아직 없다.

## 출력과 사용법

```python
result = maskara.mask(...)
result.review                 # 위치, 상태, 사유, 후보 수
result.mentions[0].resolution # 아래 상태 중 하나
result.save("masked")         # review.json도 저장. 항목이 없으면 빈 목록
```

| `resolution` | 의미 | 처리 |
|---|---|---|
| `resolved` | 현재 입력 근거로 한 소유자를 선택 | 해당 인물의 페르소나 |
| `provisional` | 인물 동일성이 확인되지 않은 문서/행 내부 그룹 | 내부 그룹의 페르소나, 검토 대상 |
| `ambiguous` | 후보가 복수이거나 정보가 충돌 | 소유자 없이 값 기반 치환, 검토 대상 |
| `unresolved` | 소유자를 정할 근거 부족 | 소유자 없이 값 기반 치환, 검토 대상 |
| `not_applicable` | ID 등 인물 소유자와 무관하게 값으로 치환하는 범주 | 기존 정책 적용 |

`evidence`는 `multiple_candidates`, `conflicting_row_values`, `name_only` 같은 고정 사유 코드다. 후보의 실제 키·이름·연락처는 기록하지 않고 `candidate_count`만 기록한다. 위치를 찾기 위한 입력 이름·열 이름은 유지된다. 점수처럼 보이는 신뢰 확률을 임의로 부여하지 않는다.

검토 파일은 **승인 인터페이스나 반출 차단 장치가 아니다**. 보류 상태도 출력 파일에 포함되고, 유지 정책이 있는 지역·인구통계 등은 기존 정책을 따른다. 소유자 없는 값 기반 치환에서는 같은 대체값이 나온다고 같은 인물을 뜻하지 않는다. 검토 후 정답 소유자 반영 기능은 후속 작업이다.

이 변경으로 이전의 이름만 이용한 문서 간 연결은 끊어진다. 임시 인물의 범위는 입력 이름·행 위치·열 위치이므로 행을 재정렬하거나 배치를 나누면 같은 인물을 유지한다는 보장이 없다. 문서·실행 간 안정적인 인물이 필요하면 명시적인 subject 키와 같은 vault/namespace를 제공해야 한다.

## 진단 결과

```bash
uv run maskara bench-identity --out runs/identity
uv run maskara bench-identity --cases independent-cases.json --out runs/identity-independent
uv run maskara bench --corpus linked --system maskara --qa linking --out runs/identity/linked-regression
```

기본 fixture는 [identity-cases.json](../../src/maskara/bench/data/identity-cases.json)이다. 동명이인, 공유 연락처, 약칭, 표 없는 이름, 날짜, 타입 충돌을 포함한 **자체 작성 32개 사례·48개 mention**이다. 정답 소유자는 scorer에만 들어간다. 탐지 문제를 분리하려고 resolver에는 정답 span 위치·범주를 제공한다. 실제 탐지 성능, 독립 고객 자료, 자연적인 사례 비율을 평가한 결과는 아니다.

| 지표 | 변경 전 | 변경 후 |
|---|---:|---:|
| 확정한 연결 | 46/48 | 26/48 |
| 정답 소유자를 맞힌 연결 | 26 | 26 |
| 충분한 근거 없이 확정한 연결 | 20 | 0 |
| 연결 정밀도 | 56.52% | 100% |
| 연결 재현율 (정답 소유자가 있는 26개 기준) | 100% | 100% |
| 보류율 | 4.17% (2/48) | 45.83% (22/48) |

`provisional`도 확정 연결로 세지 않는다. 정답 `owner: null`은 단일 소유자를 확정할 근거가 없다는 뜻이므로, 이 항목을 특정 인물로 확정하면 오답이다. 따라서 20건은 실제로 서로 다른 사람임을 독립 검증한 수치가 아니라, 이 진단 정책에서 근거 없이 확정한 건수다. 문제를 겨냥해 작성한 회귀 사례이므로 이 100%를 일반 정확도로 광고하면 안 된다.

기존 linked 441문서에서는 rules+known 조건의 QA **250/250**을 유지했다. 직접식별자 전체 잔존률도 **0.03%**로 같았다. 다만 일관성은 **99.45% → 99.15%**, 구별성은 **96.89% → 96.58%**로 낮아졌다. 연결 보류와 문서 범위 변경에는 관계 보존 비용이 있다. linked도 자체 합성 데이터이고 reader가 정답 위치·구조를 받으므로 이 QA는 일반 언어 이해나 보호 수준을 입증하지 않는다.

변경 전후 진단·linked 결과·fixture와 코드 해시는 [identity-evidence.json](identity-evidence.json)에 저장했다. 표 정보 충돌, 열 순서 불변성, scope 충돌, 원본값 없는 검토 파일, 원본 gold 소유자와 추론 경로의 분리는 별도 통합 테스트로 검증한다.

## 남은 작업

독립적으로 주석한 고객/상담사/보호자·동명이인·연락처·공동 사건 자료를 확보하고, 정책 조정용 데이터와 최종 평가 데이터를 분리해야 한다. 이번 자동 보류는 역할·문장 의미를 이해하는 공지시 해석이 아니다. 공유 사건의 시간 관계, 사용자 수정 반영, 보류량을 줄이면서 오연결을 억제하는 기준, 텍스트·표·반복 반출 공격 평가는 후속이다.
